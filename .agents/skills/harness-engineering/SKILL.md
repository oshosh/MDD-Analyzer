# 하네스 엔지니어링

기획과 구현 사이에 검증 계약을 만들고, 완료 판단을 에이전트의 자기 보고가 아닌
관찰 가능한 증적으로 바꾼다. 단순 문구·문서 수정처럼 동작이 바뀌지 않는 작업에는
과도한 E2E를 추가하지 않는다.

## 시작 전: 검증 계약 만들기

작업 요청에서 다음을 추출한다.

1. 사용자가 실제로 수행하는 핵심 시나리오와 성공 결과
2. 변경하면 안 되는 데이터·수식·UI·호환성 제약
3. 각 조건을 확인할 가장 낮은 비용의 검증 계층
4. 실제 외부 의존성이 필요한지와 fixture 또는 mock으로 분리할 범위

제품 결정이 빠져 있어 완료 조건이 달라질 수 있으면, 구현 전에 그 선택만
사용자에게 확인한다. 나머지는 합리적인 가정과 함께 진행한다.

## 검증 계층 선택

- **단위 테스트**: MDD 공식, 정규화, 포맷 변환처럼 입력과 출력이 결정적인 로직.
  정상값뿐 아니라 경계값, 결측값, 오류값을 포함한다.
- **통합 테스트**: Route Handler, Zod 스키마, 여러 모듈의 조합. 외부 데이터는
  fixture로 고정해 실패 원인을 제품 코드와 외부 서비스로 분리한다.
- **E2E**: 사용자가 브라우저에서 수행하는 핵심 경로. 화면에 보이는 결과와 오류
  상태를 검증하며, 내부 구현 세부 사항을 선택자로 삼지 않는다.
- **시각 검증**: 표·차트·모바일 레이아웃처럼 구조만으로 부족한 변경. 390px와
  414px에서 오버플로우와 주요 화면 상태를 확인한다.
- **도구·설정 하네스**: 에이전트 지침, 플러그인, 설정처럼 코드 테스트가 아닌 것.
  설정 파일 존재 여부와 해당 도구의 실제 진단 출력을 함께 확인한다.

## 구현 중 규칙

- 기능별 완료 조건마다 적어도 하나의 검증을 매핑한다. 하나의 광범위한 스모크
  테스트로 모든 조건을 주장하지 않는다.
- E2E는 실제 가치가 있는 사용자 경로에만 추가한다. 새로운 흐름을 만들기 전에
  페이지 진입점, 테스트 데이터, 로딩·오류 상태를 확인한다.
- 실시간 금융 데이터에 기대값을 고정하지 않는다. 계산·정규화 테스트는 fixture를
  사용하고, 라이브 호출은 별도의 통합 점검으로 보고한다.
- 실패한 검증을 억지로 우회하거나 삭제하지 않는다. 원인, 영향, 다음 조치를
  결과에 남긴다.

## 완료 전 점검

현재 프로젝트에서는 먼저 `pnpm run verify`를 실행한다. UI 흐름이 변경됐다면
Playwright E2E와 대상 모바일 뷰포트 검증을 추가로 실행한다. 실행 환경이나
브라우저가 없어 수행할 수 없다면, 누락된 의존성·명령·대체 검증을 구체적으로
기록한다.

작업 결과에는 "무엇을 바꿨는가" 외에 "어떤 완료 조건을 어떤 증적으로
확인했는가"를 짧게 보고한다.
